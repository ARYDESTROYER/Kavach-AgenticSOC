# Agentic SOC 0.2.0

Agentic SOC **0.2.0** opens documentation line **0.2**. It is the first release since
v0.1.1 to carry what was built on `Testing` after 0.1.12, and it folds in the 0.1.13
candidate, which was never tagged (see [Agentic SOC 0.1.13](0.1.13.md)). This page is
the release record: what is new, what changes for scripts and operators, the measured
migration and rollback evidence, the signed artifacts, and how to verify them.

The intended tag date is **2026-11-27**, the date of the `[0.2.0]` heading in
`CHANGELOG.md` and of the What's new notes. `scripts/check_version.py` requires the two
dates to match each other on `main` and on the tag, but no gate compares them with the
day the tag is cut. So if the tag slips past that day, a follow-up change through
`Testing` re-dates the CHANGELOG heading and the notes before the tag is created: the
`[0.2.0]` heading, the notes `date` and the newest update's `date`, and the intended tag
date in this paragraph. The same change runs `python3 scripts/build_release_notes.py`
and `python3 scripts/build_app_knowledge.py` and commits what they regenerate, because
CI checks both outputs.

!!! warning "A candidate is not an installable Stable release"

    Branch content, a version string, an image tag or a signature alone is not
    update authority. Version 0.2.0 is installable only after the exact accepted
    `main` commit has the immutable annotated tag `v0.2.0`, the tag and release
    workflows pass, all three public pinned images and signatures verify, the
    canonical plan and bundle publish, and canonical v0.1.1 supervised-update plus
    browser acceptance succeeds. Until then the last verified installable Stable
    release is v0.1.1. Never move or reuse the tag.

## What is new

### See the AI agent on a case

While the AI investigates a case, the queue row, the case header, the Case Manager
navigation count and the close and bulk dialogs show it. The header chip reads "AI
working · m:ss", or "AI queued" while the run waits for a slot, and opens the five steps
and who started the run. The run's result stays authoritative: the close dialogs warn
that a close made now will be replaced by the run's result, and the Inbox says so when
it happens or when a run you started ends. Reinvestigate no longer waits for the run to
finish. See [Case Manager](../analyst/case-manager.md#when-the-ai-is-working-on-a-case).

### A segregated Case Manager

The case page has six tabs with one lane each: Brief, Evidence, AI investigation,
Response, Activity and Chat, on Alt+1 to Alt+6. Alt+2, Alt+4 and Alt+5 changed meaning,
and Chat moved to Alt+6. A compact header with one meta strip, the case facts inspector
on `]` and the queue fold on `[` give the content its space back. Old `#/case_manager`
links with a `tab` still open the right tab. See [Case Manager](../analyst/case-manager.md#read-the-workspace).

### Every number explains itself

Hover a score, verdict, SLA, cost or dashboard figure for a one-line formula with the
real values; click it for the inputs, the steps, the rounding and where each value came
from, with Copy calculation. New risk scores record their inputs and the weights in
force, and each decision records the thresholds it compared. A case scored or decided
before 0.2.0 says so instead of inventing a record. See
[Explainable numbers](../analyst/explainable-numbers.md).

### Every case record is reachable

The Evidence tab re-reads the case's own raw events on the read-only log client, the
usage sheet lists every model call with the rates behind its cost, and View all fields,
the trace step details and the history reasons show the rest. See
[Every record of a case](../analyst/case-manager.md#every-record-of-a-case).

### A quiet sign-in page

The sign-in page uses the Console's own colours, has one short entrance and nothing
moving afterwards, and offers "Remember me" without a duration. See
[Authentication](../administration/authentication.md#remember-me).

### A release tracker under Communication

When a newer release is installed, each person sees a short welcome once after signing
in. The **Notifications** navigation group is now **Communication**, with **Inbox** and
**What's new**, a release tracker with notes and screenshots for every release. Accounts
created after the release is installed start with the welcome marked seen. See
[What's new](whats-new.md).

### Security and access

With role-based access on, every read asks for the grant of the data it returns. An
account an administrator created or reset must change its password before any other
request. Ten wrong second-factor codes lock second-factor checks for the account. A
password change signs out the other sessions. Only a stored Super admin with a fresh
sign-in can change single sign-on. The application-wide bug hunt confirmed 81 issues and
fixed 75; the other 6 were duplicates. See [Authentication](../administration/authentication.md)
and [Permissions](../reference/permissions.md).

## Compatibility and API changes

Scripts and integrations that call the API should check these before upgrading.

- **Runbooks.** Writes under `/api/playbooks*` and `POST /api/cases/{id}/run-playbook`
  answer `410 runbooks_moved`. The `GET /api/playbooks*` reads stay as aliases for this
  release only. The grants `playbooks:read`, `playbooks:run` and `playbooks:manage` map
  onto `runbooks:*` in every grant and deny layer.
- **Role-based access switch.** `PUT /api/settings` answers `409 rbac_switch_moved` when
  a body would change `rbac.enabled`; the switch is `PUT /api/rbac` (stored Super admin,
  fresh sign-in).
- **Read grants.** With role-based access on, a custom role without the grant of a read
  gets `403` and an Access denied audit row. The built-in roles hold every such grant.
- **Accounts.** `403 password_change_required` on every route except a short
  self-service list until a flagged account changes its password. Second-factor lockout
  answers `429`. `POST /api/auth/refresh` is deprecated and answers
  `401 session_invalid`; no sign-in issues a refresh token. `AUTH_TOKEN_HOURS` is capped
  at 144.
- **Single sign-on.** A provider's default role or group mapping must be a built-in
  role (`422` otherwise).
- **Reinvestigate.** `POST /api/cases/{case_id}/reinvestigate` with `wait: false`
  answers `202` at once; a second request answers `409 investigation_running`; a closed
  case is reinvestigated in place or answers `409 open_case_exists`.
- **Audit before visible.** Settings, account, source, runbook and dashboard changes
  write their audit row first and answer `503 audit_unavailable` when the audit log
  cannot be written. Audit client addresses come from `X-Forwarded-For` only through a
  proxy listed in `TRUSTED_PROXIES` (default `tlsoc-webui`).
- **Chat** sits outside the daily and monthly AI budget. Its only spending bound is the
  optional `chat_agent.chat_daily_cap_usd`. Chat limits version 2 triples the "Timeouts
  and capacity" defaults.
- **New routes:** `GET /api/investigations/active`, `GET /api/cases/{id}/events`,
  `GET /api/cases/{id}/usage` and `GET /api/metrics/explain`. Every new response field is
  additive.

The [API reference](../reference/api.md) lists every route and status.

## Upgrade steps

Read [Upgrade operations](../operations/upgrades.md#changes-that-need-attention-when-upgrading-to-this-build)
first. In order:

1. **Set the update repository.** Add this line to `.env` on the deployment host:

    ```text
    AGENTIC_SOC_UPDATE_REPOSITORY=ARYDESTROYER/Kavach-AgenticSOC
    ```

    The bootstrap refuses to run when the line is missing, when it still names
    `ARYDESTROYER/Agentic-Kibana` in any letter case, or when it names the new
    repository in the wrong letter case, because the signing identity is
    case-sensitive. It prints the exact line and never edits `.env` itself.

2. **Back up** the state store and the deployment secrets, as for any upgrade, to a
   place outside the deployment checkout: the bootstrap refuses a checkout with files Git
   does not ignore.

3. **PostgreSQL: the audit id column.** Every published release up to v0.1.12 created
   `audit.id` as a 32-bit integer. On its first start, 0.2.0 widens the column and its
   sequence to `bigint` in place. PostgreSQL rewrites the table and its indexes under an
   exclusive lock, so audit writes wait until it is done. Measured at release
   preparation with the backend's own migration code
   (`ensure_schema_migrations`) on PostgreSQL 16.15 with default settings, on a 4 vCPU
   virtual machine with 16 GB of memory, on an audit table built like v0.1.1's and
   filled with rows shaped like its poll row (a 365-byte document each):

    | Audit rows | Table and indexes | Widening |
    | --- | --- | --- |
    | 1,000,000 | 0.61 GB | 4.9 s and 4.1 s (two runs) |
    | 5,000,000 | 3.06 GB | 25.0 s |
    | 10,000,000 | 6.12 GB | 44.3 s |

    The time follows the table's size on disk, 7 to 8 seconds per GB here; other disks
    and larger rows change it. Read yours with
    `SELECT pg_size_pretty(pg_total_relation_size('audit'));`. The rewrite needs free
    disk about the size of the table. A second start finds `bigint` and does nothing.
    The signed plan keeps its 300-second backend rollout timeout, because 10 million
    rows took 44 seconds. On a very large audit table, run the two statements yourself
    in a maintenance window before the upgrade, with the backend stopped:

    ```sql
    ALTER TABLE audit ALTER COLUMN id TYPE bigint;
    ALTER SEQUENCE audit_id_seq AS bigint;
    ```

    Then start the v0.1.1 backend again. At its first start, 0.2.0 finds the column
    already `bigint` and does nothing.
    v0.1.1 reads and writes the widened column unchanged (see [Rollback](#rollback)),
    which is why the plan's migration strategy stays `none`.

4. **Elasticsearch state.** At startup the backend adds the audit mapping upgrade and
   two cases mappings (`risk_breakdown.inputs`, stored and never indexed, and
   `awaiting_reason`) to the templates and to every live index that lacks them. It only
   adds. The manual audit template step is needed only when the backend logs that it
   could not read or change a template; see
   [Applying the Round 14 audit template](../operations/upgrades.md#applying-the-round-14-audit-template).

5. **Runbooks.** On the first start every stored procedure and reference runbook is
   converted once into a runbook by the system actor `runbook_migration`, audited, before
   the library is used. See [Upgrade operations](../operations/upgrades.md#round-14-changes).

6. **Tell people what they will notice:** the six case tabs and the changed Alt keys,
   the forced password change, the MFA lock, sign-out of other sessions after a password
   change, the Communication group, and that Reinvestigate updates a closed case in
   place.

Demo Mode never reads a tenant source, and its spend is simulated and marked so
(`price_basis: demo_simulated`).

## Rollback

An image-only rollback is the documented recovery path, and the updater performs it
automatically when an upgrade fails readiness. Every field 0.2.0 stores is additive.

**The v0.1.1 rehearsal.** The canonical rollback target in the field is v0.1.1, the only
installable Stable release before 0.2.0. At release preparation it was rehearsed from
source (`ba179651a7b63d6352ad346fd633e1460f3a4d39` with its pinned requirements, against
this checkout) on PostgreSQL 16.15 with pgvector 0.6.0, in the order of a real upgrade:
v0.1.1 first on a fresh database, then 0.2.0 on that database with the rollback lane's
release-N writes, then v0.1.1 again, then 0.2.0 again. Twice, once with v0.1.1 only
reading and once with it saving cases, an account, the preferences and the settings.
The result:

- v0.1.1 boots on the data 0.2.0 wrote, answers `/api/health/ready` with 200 and
  `/api/health` with `ok`, lists and opens the cases 0.2.0 wrote, saves them, reads the
  audit log and appends to it, and reads the case spend from the ledger row 0.2.0
  wrote. Its log holds no error and no traceback. 0.2.0 then starts healthy again.
- The widened `audit.id` stays `bigint`, and v0.1.1 writes its audit rows into it.
- **Settings v0.1.1 does not model are reset.** Its graceful stop, and any settings save
  it makes, rewrites the settings document without them. Back on 0.2.0 they read as
  their defaults: the sections `analyst_rule_policies`, `auto_close_review`,
  `chat_agent`, `evidence_fields`, `evidence_max_chars_per_event`, `precedent`,
  `replay_capture`, `resilience` and `team_activity`, and the newer keys inside `caps`,
  `enrichment`, `rag`, `rbac`, `runbooks`, `session_policy` and `threshold_tuning` (for
  example `runbooks.auto_attach`, `session_policy.remember_me` and
  `threshold_tuning.auto_apply_confirmed`). In each log source the declared severity
  ceiling `severity_scale_max` is reset too, so a Wazuh source reads its seeded 16 again
  and any other source the 0 to 100 identity, which can change its severity bands; in
  each suppression rule `approval_proposal_id` is reset. Note the values you changed and
  set them again after the return.
- **Per document,** a case v0.1.1 saves loses its recorded risk inputs (it then reads
  "not recorded", with its score and factors unchanged), and an account it saves loses
  its second-factor lock counter. Ledger rows keep their rates. The What's new marker,
  the auto-close review grade and the case screenshots survive.

This rehearsal ran the release's source, not a v0.1.1 Compose deployment through the
updater. The image-level rehearsal on a Docker host stays maintainer action M5. It needs
a published, signed 0.2.0 release, so it runs on the release of the M7 dress rehearsal
before the tag, or on 0.2.0 itself after publication:

1. Build a disposable PostgreSQL Compose deployment from the `v0.1.1` tag, as its own
   DEPLOY.md installs it (v0.1.1 published no images):
   `docker compose -f deploy/docker-compose.agnostic.yml up -d --build`. Let v0.1.1
   write its own state: cases, an account, the preferences and the settings.
2. Update it to 0.2.0 as in [Operator bootstrap](#operator-bootstrap), and write data
   on 0.2.0. On the dress rehearsal's release, name the test repository instead of
   `ARYDESTROYER/Kavach-AgenticSOC`, in the remote URL and in
   `AGENTIC_SOC_UPDATE_REPOSITORY`.
3. Roll that update job back with **Roll back** in the Console's update panel, as the
   built-in Super admin after signing in again (the route also needs
   `system_updates:rollback`). A post-success rollback restores the v0.1.1 images and
   leaves PostgreSQL as 0.2.0 wrote it.
4. Check the narrower pass condition above on v0.1.1, then update to 0.2.0 again and
   check that it starts healthy.

The source rollback lane is not that rehearsal. Run as
`scripts/rollback_lane.py --previous-release ba179651a7b63d6352ad346fd633e1460f3a4d39`,
it builds v0.1.1 from source with `git archive`, boots 0.2.0 first on a fresh database,
and checks features of the earlier build that v0.1.1 does not have (the jobs route and
the `runbooks.*` choices it expects back). It stops at the first of those checks, so it
cannot pass against v0.1.1, and the pass condition for v0.1.1 is the narrower one above. The receipt of this
rehearsal and of the widening timings is kept with the release preparation's acceptance
records in the source repository.

The rollback to the previous release the lane pins, and the Round 14 and Round 15
rollback notes, are in [Upgrade operations](../operations/upgrades.md#rolling-back-from-020)
and [Known limitations](known-limitations.md#rolling-back-from-020-loses-what-the-earlier-build-cannot-keep).

## Operator bootstrap

Run the bootstrap in the checkout that runs the canonical deployment, on its host. The
bootstrap reads `.env` from the checkout it runs in, and that file must be the
deployment's own `.env`, with `AGENTIC_SOC_UPDATE_REPOSITORY=ARYDESTROYER/Kavach-AgenticSOC`
added. Never create a new `.env` from `.env.example` for an upgrade: new
`TLSOC_PG_PASSWORD` and `TLSOC_AUTH_JWT_SECRET` values would not match the existing
database and sessions. `.env` is ignored by Git, so it stays in place when the checkout
moves to the tag. Any other file Git does not ignore, such as a database dump or a copy
of `.env`, leaves the checkout unclean and the bootstrap refuses it, so keep backups
outside the checkout.

The bootstrap also checks that the tag is contained in `origin/main`. v0.1.1's install
guide made a shallow clone of one tag (`git clone --branch v0.1.1 --depth 1`), which
has no `origin/main`; the `set-branches` line and the unshallow fetch below give it one:

```bash
cd /path/to/the/deployment/checkout
git remote set-url origin https://github.com/ARYDESTROYER/Kavach-AgenticSOC.git
git remote set-branches origin '*'
if [ "$(git rev-parse --is-shallow-repository)" = true ]; then
  git fetch --tags --unshallow origin
else
  git fetch --tags origin
fi
git switch --detach v0.2.0
test "$(shasum -a 256 deploy/docker-compose.agnostic.yml | awk '{print $1}')" = \
  "$(tr -d '[:space:]' < deploy/update-base-v1.sha256)"
test "$(git cat-file -t v0.2.0)" = "tag"
test "$(git describe --tags --exact-match)" = "v0.2.0"
test "$(git rev-parse HEAD)" = "$(git rev-parse 'v0.2.0^{}')"
test -z "$(git status --porcelain --untracked-files=all)"
./scripts/bootstrap-updater.sh
```

From then on, run `./scripts/agentic-soc-compose.sh` from this checkout. The Console must then report `v0.2.0 · Stable`, and its
release manifest and the healthy backend must agree on the exact commit.

## Known limitations

The full list is [Known limitations](known-limitations.md). New in 0.2.0:

- The investigation registry, the investigation gate and the realtime bus are process
  local; one backend replica only.
- Push sources correlate over the last 500 events in memory, and a push case's events
  cannot be re-read.
- Recorded risk inputs and decision gates start with 0.2.0; older cases read "not
  recorded" or use today's settings.
- An image-only rollback to v0.1.1 resets the settings v0.1.1 does not model, and drops
  recorded risk inputs and lock counters on the documents it saves (see [Rollback](#rollback)).
- The PostgreSQL audit id column is widened in place at the first start.
- The repository rename changes the update trust root; the `.env` line is required.
- Chat is the sixth case tab until it moves into the case facts inspector.
- Single sign-on maps only built-in roles.
- Three accessibility findings remain (a minor empty table header, a moderate heading
  order and a moderate region), each needing a change across several pages.
